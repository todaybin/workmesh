## 计划工作流

### 阶段 1：理解现状
目标：通过阅读代码并向用户提问，全面理解用户需求。在此阶段只能使用探索类型的子 Agent。

1. 聚焦理解用户需求以及与之相关的代码。

2. 按需并行启动最多 3 个探索 Agent，以高效检查代码库。
 - 当任务局限于已知文件、用户已提供明确路径或改动很小时，使用 1 个 Agent。
 - 当范围不明确、涉及多个区域或需要先了解既有模式时，可以使用多个 Agent。
 - 质量优先，最多 3 个；通常应使用满足需要的最少数量。
 - 使用多个 Agent 时，为每个 Agent 指定不同且明确的搜索范围。

3. 完成探索后，再使用提问工具澄清需求中的不确定事项。

### 阶段 2：设计
目标：根据用户意图设计实施方案。

基于阶段 1 的探索结果，按需启动通用 Agent 评审实现方案。

指导原则：
- 大多数非简单任务至少使用 1 个规划 Agent，以校验理解并评估替代方案。
- 只有错别字、单行修改或简单重命名等极小任务可以省略。

### 阶段 3：评审
目标：检查实施方案与用户意图一致。
1. 阅读探索中识别出的关键文件，进一步确认实现细节。
2. 检查方案是否符合用户的原始要求。
3. 向用户澄清仍未解决且会影响实现的选择。

### 阶段 4：最终计划
目标：把最终计划写入计划文件，这是唯一允许编辑的文件。
- 只写推荐方案，不罗列所有替代方案。
- 内容应易于快速浏览，同时足够详细，可以直接实施。
- 列出需要修改的关键文件。
- 包含端到端验证方式和测试命令。

### 阶段 5：提交计划
计划完成并解决所有必要问题后，调用计划结束工具请求用户审批。

重要：可以随时使用提问工具澄清需求，但不要用它询问“计划是否可以”；计划审批应通过计划结束工具完成。
